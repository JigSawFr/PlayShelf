# Code layout

Part of the [contributor's guide](../../CONTRIBUTING.md).

PlayShelf is built on the technical base of [PlayGuard](https://github.com/JigSawFr/PlayGuard). What the apps share lives in the kit, [boreale-kit](https://github.com/JigSawFr/boreale-kit) (the submodule `library/boreale-kit/`, pinned on a release tag: its `util/`, `core/` and `sim/`), and, until they move there, in **`source/kit/`**; what is PlayShelf's own lives beside it, in `source/`.

| Folder | What it holds |
|---|---|
| `library/boreale-kit/source/core/` | The C layer over libnx (platform, system information, local time, crash handler, start-up timing, the read-only switch). Each module has a plain-C header; the desktop build replaces the console's ones with `library/boreale-kit/source/sim/` |
| `library/boreale-kit/source/sim/` | The simulated console of the desktop build, driven by `PLAYSHELF_SIM_*` variables ([the simulator](simulator.md)) |
| `library/boreale-kit/source/util/` | Plain C++, most of it host-tested: HTTP (libcurl, TLS verified; byte ranges streamed), JSON, SHA-256, AES-128, secrets sealed for this console (`secret_box`, with `core/device_key.h`), zip, paths and atomic writes, migrations, session logs and crash reports, updates, development builds, GitHub sign-in, diagnostics |
| `source/kit/action/` | Flows: `*_logic` files are plain C++ (host-tested), `*_flow` files drive the dialogs and screens |
| `source/kit/ui/`, `source/kit/view/` | What the kit adds to the Cadran look: the app's `ui::` helpers (background tasks, the SD card's writes, `config.json`, result codes, the console's clock and system, the read-only mode, `ui::app_hooks`) and its own views (the loading screen's mark and dial, the release notes, the funding cards, a development build's cell, Made in France). Cadran itself (the frame and its rail, dialogs and pickers, lists, palettes, icons, effects, Markdown, the language and theme changed while the app runs) is [Aurore](https://github.com/JigSawFr/Aurore)'s, in `library/aurore/library/*/cadran/` ([its guide](https://github.com/JigSawFr/Aurore/blob/main/docs/cadran.md)) |
| `source/kit/activity/`, `source/kit/tab/` | The shared screens (loading, update, development builds, diagnostics, changelog, what's new) and the base of every tab |
| `source/install/` | The install formats, plain C++ with no libnx nor Aurore, host-tested and fuzzed (`tests/install/`, `tests/fuzz/install_*`): AES-128 (XTS with Nintendo's tweak, CTR, ECB), RSA-2048-PSS, the PFS0 and HFS0 archives (an NSP, a game card's partitions) and a game card's header, a title's content meta (CNMT) and the record ncm keeps of it, an NCA's header and the content meta inside a `.cnmt.nca`, and a content as it arrives (`content_stream`: a `.nca`, or a `.ncz` decompressed with zstd and encrypted again) made the bytes of its NCA, checked against the content meta's SHA-256; a package (`package`: an NSP, NSZ, XCI or XCZ, read through a `Source` of ranges) installed as one transaction (`installer`: everything checked before anything is written, every failure undone; paused and taken up again from its journal, a `.nca` where it stood) on a `Console` interface (ncm, its content meta database, ns and es); a range fetched over several connections at once and handed on in order (`split_stream`, `tests/split_stream/`); a package whose first bytes are in a file fetched ahead (`prefix_source`, `tests/prefix_source/`). the firmware's compression layer of an NCA section (`compressed_storage`: the blocks and bucket tree, built and read back; the codec is the caller's, liblz4 in the tests). a RomFS section's integrity tree (`ivfc`: five levels of SHA-256 hashes over the data, built and verified); a Program NCA made over with its RomFS compressed (`recompress`), and its content meta and `.cnmt.nca` (`recompress_meta`); an installed title made over as a transaction that can be undone, journaled and recovered after a crash (`compress_title`). The console's keys come from outside (`NcaKeys`) |
| `source/download/` | The downloads' queue, plain C++ host-tested (`tests/download_queue/`): its jobs kept in `queue.json` with each install's journal (no credential: a library server's id), a running job back as paused after a restart, the next job, the jobs by game and their timeline, the speed and the time left, the placeholders no job keeps; and what to do with a failed one (`recovery`, `tests/download_recovery/`): its cause read from its error, PlayShelf's own tries, the remedies offered, the server's other address, a package installed by now or found again in a catalogue |
| `source/library/` | The library's neutral parts, plain C++ host-tested (`tests/library/`): addresses made absolute and https only, title ids and kinds, which of a server's addresses to use (`server`, `tests/library/`), the profiles kept in `servers.json` (`servers`, `tests/library_servers/`: a name, addresses and the server's `uid`; schema 1 carried over once), the neutral catalogue the screens read (`catalog`: items with their SHA-256, sections), the cheat files on the SD card (`services`, `tests/library_services/`), and a catalogue gathered by game, searched and sorted (`titles`, `tests/library_titles/`); the console's games by title (`installed`, `tests/library_installed/`: a base game, its update, its add-ons); when each game was first seen on a server and the wishlist's file (`seen`, `tests/library_seen/`); how well known each game is, its trend and its critics' score (`popular`, `tests/library_popular/`), each game's traits and Steam audience and the games most like it (`signals`, `tests/library_signals/`), the games still to come and how many follow each (`upcoming`, `tests/library_upcoming/`), where each of the best known games is read, by language (`reach`, `tests/library_reach/`), the other stores a game is sold on (`also`, `tests/library_also/`), all read from what [Atlas](https://github.com/JigSawFr/Atlas) makes every week (`resources/data/` has copies of `popular.json` and `games.json`); the games to suggest from all those signals and the console's play, each with its reason (`recommend`, `tests/library_recommend/`), and the rules of Home's Atlas rows: which games are worth an evening, much read in the console's language, or missing from the console's series (`rows`, `tests/library_rows/`) |
| `source/homebrew/` | Installing a homebrew package from a server onto the SD card (SPEC § 8.3), plain C++: the plan checked by the SDK, a single file or an archive written aside and checked against its manifest, then moved in; what an update no longer ships removed; the installed ones kept in `homebrew.json` (schema 1, never written over a newer one) (`install`; `tests/homebrew_install/`; `tests/homebrew_cycle/` runs a whole life: read, installed, updated by a delta, removed) |
| `source/lantern_app/` | PlayShelf's side of [Lantern](https://lantern.boreale.dev), over the SDK in `library/lantern-sdk/` (a submodule, never copied; its client does the protocol): the credentials kept sealed on the SD card (`credential_store`, `tests/lantern_store/`), a server read into the neutral catalogue (`session`, `catalog_map`: the address chosen, the key pinned at pairing, the apps and sections; `tests/lantern_session/`, `tests/lantern_catalog/`), a package fetched whole and verified for the fetch ahead (`package`), or put together from an older copy on the SD card and the ranges that differ (`delta`; `tests/lantern_delta/`), read from a peer of the network when one holds it (`peers`, `peers_lookup`; `tests/lantern_peers/`) or read by signed ranges as the installer asks (`range_source`; `tests/lantern_range/`), a server's homebrew catalogue for its tab (`homebrew_map`; `tests/homebrew_map/`), the cheats, saves and requests (`services`), the LAN discovery (`discovery`, `system`: random bytes, the clock, the UDP socket; `tests/lantern_discovery/`, `tests/lantern_system/`), a port's game data looked for on the SD card (`port_data`; `tests/lantern_ports/`), the console serving its files to peers (`peer_book`: its uid, the grant keys, the files held; `peer_service`: the responder over the SDK's `PeerGate` and its two sockets, one connection at a time; `tests/lantern_peers_serve/`; the flow is `source/action/peer_flow`) and the transport of each platform (`platform`: libcurl on a PC, mbedTLS on the console) |
| `source/saves/` | A game's save as a zip archive (`archive`, plain C++ on zlib, `tests/save_archive/`, `tests/fuzz/save_archive`): made from the save's folder as it is read, read back entry by entry with each name, size and CRC-32 checked |
| `source/titledb/` | The title database, plain C++ host-tested (`tests/titledb/`, `tests/titledb_store/`): CyberFoil-DB's packs read where they lie (`CFTITLE1` names, publishers, versions; `CFICONP1` icons), its manifest (with CyberFoil's aliases, HTTPS only), a title list read as it streams and made a titles pack (Ghostland's, a Tinfoil index's `titledb` such as NXMeta's), each source's folder (packs named after their SHA-256, `state.json` written once they are checked, a cut part resumed) and the sources by priority |
| `source/core/` | PlayShelf's own C layer over libnx: `awake.h` (no automatic sleep while downloads run), `games.h` (an installed game's name, shown version and icon, from ns' control data; the room it takes and the SD card's; a game deleted), `saves.h` (the console's users, the games each has a save of, a save mounted as a folder and committed), `play.h` (how much each game was played, from pdm:qry), `install.h`, the services an install goes through (ncm's content storage and content meta database, ns's application records, es's tickets, spl's NCA keys). Switch only; the desktop build swaps in `source/sim/` |
| `source/sim/` | The desktop build's console for `source/core/`: `sim_install.cpp`, a console in `playshelf_data/sim_console/` with the host tests' keys; `sim_games.cpp`, a game's control data as files in its `control/`, a game deleted from its `meta/`; `sim_saves.cpp`, the users and their saves as folders in its `saves/`; the simulators' demo (`sim_demo.hpp`: `sim_demo_http.cpp`, the demo library server and the demo's answers of Atlas, Nlib API and a title database, in place of the network's on the desktop through `util/http`'s stand-in; `sim_demo_seed.cpp`, on a first start the demo's server, first games, wishlist and title database on the console); and the web simulator's own (`web_http.cpp`, the network as a console without one but for the demo's answers; `web_page.cpp`, what the page calls while PlayShelf runs) |
| `web/` | [The web simulator](../../web/README.md)'s page (its settings panel, steps, tour, service worker) and its demo, made from `tools/web_demo_games.json` (made-up games): `tools/web_demo.cpp`, its library server, Atlas' files and the console's first games; `tools/web_demo_art.py`, their pictures (SVG scenes of `tools/web_demo_scenes.py` rendered in Chromium), Nlib API's answers and a title database; `tools/web_smoke.py` plays it in headless Chromium, `tools/check_web_params.py` checks its settings against the simulator's variables |
| `site/`, `docs/` | [The website](../../site/README.md): its texts in each language and its styles (`site/`), the documentation it publishes (`docs/`, `docs/fr/`); `tools/build_site.py` builds it, `tools/site_screenshots.py` takes its screenshots, `tools/check_site_links.py` and boreale-site's `tools/site_layout.py` check it; what Boréale's sites share (languages and the language kept, header menus, links out, fonts, marks, Umami's tracker, the checks) is the submodule `library/boreale-site` |
| `source/action/` | PlayShelf's own flows: `homebrew_flow` (a server's homebrew read, a package fetched and installed, what is installed kept in the book), `install_flow` (packages installed one after the other in one dialog: Help & diagnostics › developer tools › Install from a URL), `download_flow` (the downloads' queue at work: one job after the other on a worker thread, each from its journal, paused and resumed, the sigpatches checked before the first, the orphan placeholders deleted before each, the console kept awake meanwhile, a transfer cut short paused rather than undone and tried again by itself, the next packages fetched ahead when asked; the install a job runs on its worker, read from the SD card and the server, is `download_job`), `library_flow` (the Catalogue tab's servers: a catalogue fetched and kept for the run, a LAN server's key trusted on first use, the servers of this network found, a game's items added to the downloads), `installed_flow` (the Library tab's games: what is installed by game, each one's name and icon read once a run; a game deleted), `titledb_flow` (the title databases: opened at start-up, fetched again from Preferences one source after the other, the names and icons the other tabs fall back on), `library_icons` (the covers: a server's, cached, or the title database's, WebP decoded by libwebp, else Nlib API's; a game page's banner and screenshots, scaled down; every one decoded off the UI thread, the console's icons too, and shown with `aurore::Image::setImageFromRGBA`, a texture freed with its view), `nlib_flow` (a game's details from Nlib API in PlayShelf's language, kept a week; their facts kept for good in `library/facts`, gathered as the games show), `game_page` (a catalogue's game opened on its page, from the Catalogue and Home), `insights` (what Home and the bell make of the console and its servers: every catalogue read once a run, the rows, the updates to get and **Update all**), `notices` (the notification bell's entries; `notice_logic`, plain C++ host-tested in `tests/notice_logic/`: their kinds, order and those put away), `popular_flow` (Atlas' `popular.json` and `games.json`, the ones PlayShelf came with or the newest fetched, `similar.json` and `editions.json` fetched only), `insights_index` (Atlas' `index.json`: a file is downloaded again only when it changed), `wishlist` (the games wished for, in `wishlist.txt`), `rebuilt` (the games installed from a package stored compressed and not signed by Nintendo, for which no official update is offered; `rebuilt.txt`), `not_interested` (Home's suggestions put away, in `not_interested.txt`), `services_flow` (an AeroFoil server's cheats, save backups and requests, from the Catalogue's server sheet and a game's page) |
| `source/activity/`, `source/tab/`, `source/view/` | PlayShelf's screens: the main screen, the Home (where the console and its servers stand), Library (the games on the console), Catalogue (a library server's, and its homebrew) and Downloads tabs, the homebrew's tiles and sheet (`homebrew_panel`, in the Catalogue and the Library), a library server's editor (`server_activity`), a game's page (`game_activity`: its lines, and what Nlib API knows of it), the notification bell (`notice_bell`) and its list (`notices_activity`, its entries from `insight_notices`), the SD card's room (`storage_activity`), the search of every server (`search_activity`), a game's cover (`game_tile`), line (`game_cell`) and wide banner (`banner_card`), a tab's control as a pill (`tool_chip`), a game's packages in the downloads as one line (`timeline`) |
| `source/` (outside `kit/`) | PlayShelf itself: `main.cpp`, `app.*` (its identity and modes), `util/config.*` (its settings), its screens and tabs |

The rules `tools/check_sources.py` enforces:

- **The kit includes nothing of the app** but `app.hpp` and `util/config.hpp` (the app's identity and settings). It asks anything else of the app through Aurore's `ui::hooks` (`aurore/cadran/ui/hooks.hpp`: the main screen, the tabs' positions and rail icons, PlayShelf's version, logo and read-only mode, saving the look's preferences) and the kit's own `ui::app_hooks` (`source/kit/ui/app_hooks.hpp`: the notifications, a check before PlayShelf replaces itself), which `source/activity/screen_hooks.cpp` fills in at start-up. The kit can then become a library shared with PlayGuard without untangling anything.
- `ui/`, `view/` and `util/` never include `activity/` or `tab/`; a flow includes only the screens it opens itself.
- A C file of the kit's `core/` that needs no console service is in the desktop build and in a host test (the kit's own CI checks the second).

The Cadran look: a colour is always a palette key (`cadran::kit::color("cadran/teal")`, `@theme/cadran/...` in XML), never a literal; Aurore's tests check every ink on every surface in both themes.
